# DASIA-IoT project
This repository is part of the DASIA-IoT project, focused on detecting attacks against IoT devices through power usage reads and Machine Learning.

The following papers have been published for this project:

- [Intrusion detection for IoT environments through side-channel and Machine Learning techniques](https://doi.org/10.1109/ACCESS.2024.3362670) (2024)
- [Integrating Side-Channel Power Signals and Network Traffic for Machine Learning-Based Intrusion Detection in IoT](https://doi.org/10.3390/electronics15143114) (2026)

The following repositories are included in this project:

- IOT (this repository): Contains scripts used to train and test one or more Machine Learning models, as well as scripts used to test and run them. Models can be run offline (with an existing dataset) or online (reading real-time data from a buffer).
- [IOT_pi](https://github.com/CenitS-COMPUTAEX/IOT_pi/tree/main) : Contains scripts that run on the devices to launch attacks and read power usage.
- [IOT_server](https://github.com/CenitS-COMPUTAEX/IOT_server): Contains the code of the server that can respond to attack alerts generated by the system.
- [IOT_dummy](https://github.com/CenitS-COMPUTAEX/IOT_dummy): Used to generate fake network traffic on the end devices to simulate legitimate behavior.
- [IOT_central](https://github.com/CenitS-COMPUTAEX/IOT_central): Used to launch complex scenarios that require running commands on multiple devices at once with a single centralized script.

Physically, the code in these repositories is meant to work with a setup consisting on a main device that manages several end devices, launching attacks against them and reading their power usage.

# General structure
This repository contains code and data for both stages of the DASIA-IoT project. The first stage works with power reads and "regular" models. Stage 1 was introduced in the first published paper.
The second stage of the project extends it to work with network data on top of power data. This multivariate data is represented as a time series, and is handled by "time" models. <!-- TODO: "Stage 2 was introduced in the second published paper." -->

Whenever the code mentions a "regular" dataset, it's referring to data from Stage 1 of the project, which only contains power reads. Similarly, if it mentions a "regular" model, it refers to a standard model that uses that power data to make its prediction.
If the code mentions a "time" dataset, it refers to a Stage 2 dataset, that is, a 3D multivariate time series dataset that contains both power data and network metrics. If it mentions a "time" model, it's referencing a model that reads input data as a time series and uses all or some of its features to make a prediction.

# General repository information
This is the main repository of the DASIA-IoT project. It can be used to train, test and run machine learning models. This includes both regular models and time models. It can also work with real-time data, analyzing power usage in real time and generating alerts if an attack is detected.

This repository also contains the feature selection algorithm employed during Stage 2 of the project, which determines the best metrics to use when training time models through the use of a genetic algorithm.

It also contains some utility scripts, such as [main_dataset_info.py](IOT/main_dataset_info.py), which will print information about dataset files provided to it, or [main_print_time_series.py](IOT/main_print_time_series.py), which can be used to create images displaying one or more instances of a time dataset.

# Running commands
Both this document and the [Reproduction steps document](Reproduction%20steps.md) will often contain example commands that the user can run. These commands are specified with a simplified syntax, such as `python IOT/main_train_model.py`. This simplified syntax is only valid if you performed the installation on the global environment. If you used a virtual environment, you will have to ensure your commands are run in the virtual environment. There's several ways of accomplishing this:

1. Use an IDE that can perform venv integration, allowing you to run the main scripts without having to worry about manually interacting with the venv. The only thing you should have to do is specifying the location of the venv (`.venv-iot`).
2. Activate the venv using the console
	1. Open a console in the root folder of the repository that contains the script you wish to run
	2. Change the Windows execution policy to allow running scripts from the console. To do this, run the command `Set-ExecutionPolicy -ExecutionPolicy Bypass -Scope Process`
	3. Run the venv's activation script (`.venv-iot\Scripts\Activate.ps1`). You should see the `(venv)` prefix, which confirms that the venv has been activated.
	4. You can now run call the repository's main scripts through this terminal
3. Directly call the Python executable in the venv when running commands
   1. Open a console in the root folder of the repository that contains the script you wish to run
   2. Call the scripts specifying the path to the the Python executable in the venv. For example, instead of `python IOT/main_run_model.py`, run `../.venv-iot/Scripts/Python.exe IOT/main_run_model.py`.

On top of this, make sure you always run all commands from the root folder of the current repository (e.g. `IOT/`, `IOT_pi/`), not from the folders where the scripts are located (e.g. `IOT/IOT/`, `IOT_pi/code/`).

# Models
This repository contains an implementation of the following models:

## Regular models
These models take power reads as their only input feature.

- Time Series Forest (TSF): Processes data as a time series, extracting some of its features and building a decision tree specially designed to work with temporal data.
- Feature Summary (FS): Processes data as a time series, summarizing them by calculating metrics that describes the series. These new features are passed to a Random Forest classifier, which performs the prediction.
- Random Forest (RF): Builds multiple decision trees and combines their output to make a prediction.
- Extreme Boosting Trees (XBT): Sequentially builds decision trees. Each tree tries to improve the prediction of the previous one.
- KNN: Classifies instances based on their similarity to previously seen ones.
- Support Vector Machine (SVM): Attempts to classify the data by searching for a hyperplane that divides them.
- Logistic Regression (LR): Attempts to approximate a function that can determine the class of each instance.

## Time models
These models take multivariate time series as input. The series combine power reads with network data.

- Feature Summary (FS)
- Time Series Forest (TSF)
- Supervised Time Series Forest (STSF)
- TSFresh (TSFR)
- FreshPRINCE (PFR)
- HIVE-COTE v2 (HC)
- MUltivariate Symbolic Extension (MUSE)
- Random Dilated Shapelet Transform (RDST)
- Mini-ROCKET (ROCKET)

### Time model types
The models listed above, classified by type according to ([Middlehurst et al, 2023](https://doi.org/10.48550/arXiv.2304.13029)):

- Distance-based: (None)
- Feature-based: FreshPRINCE, FS, TSFresh
- Interval-based: TSF, STSF
- Shapelet-based: RDST
- Dictionary-based: MUSE
- Convolution-based: Mini-ROCKET
- DL-based: (None)
- Hybrid: HIVE-COTE

## Training and testing the models
Models work with the data generated by other scripts, such as the power measurement scripts running on the devices (see IOT_pi repository) or the alert reception script running on the alert server (see IOT_server repository). Models take an input file (.csv for regular data and .csvh for time data) or an input folder containing multiple data files. Those input files are combined and then the resulting dataset is transformed according to several configuration parameters. See the published paper for details on how this process takes place.

After a model is tested (or trained with a certain train/test split), it outputs several files containing the test results. If multiple models are tested, a single file containing the results of all the trained models will also be created. The metrics used in the result files are the following:

- F1 score: The F1 score is the harmonic mean between recall and precision. It's a value between 0 (worst) and 1 (best). Since input data usually has more than 2 classes, the final F1 score was computed using the _micro_ method, which accounts for label imbalance (normal behavior instances are significantly more common in regular datasets).
- TP<sub>c</sub> (True positives, correct): Instances that represent an attack, were classified as such and the predicted attack type is correct.
- TN (True negatives): Instances that represent normal behavior and were classified as such.
- TP<sub>i</sub> (True positives, incorrect): Instances that represent an attack and were classified as such, but the predicted attack type is incorrect.
- FP (False positives): Instances that represent normal behavior but were classified as an attack.
- FN (False negatives): Instances that represent an attack but were classified as normal behavior.

## Running the models
Once created, the models are dumped to a folder. If the three relevant files (two .pkl files and _model_info.txt_) are present, the model can be re-used, performing predictions on new data.

When running a model, the input data is formatted the same way as when the model was created (this includes the same parameters used to transform the data). The model then performs a prediction for each row on the resulting transformed dataset.

Regular models can be run in buffer mode. In this mode, the prediction will be made on the most recent entry of the resulting dataset. If an attack is detected, the set attack response will be run.

The models support three types of predictions:

- Boolean: The model will simply try to determine if an attack is taking place or not.
- Best match: The model will try to determine the most likely class for each data point, indicating the type of attack (or attacks) that is taking place, or if no attacks are happening.
- Multi-match: The model will determine the probability of each of the classes it has been trained with, which includes the chance of no attack taking place and the chance of each possible attack combination (out of the ones it has seen during training).

## Model output
Training or testing a model will output some of the following files:

- model.pkl: File containing the trained model
- scaler.pkl: File containing the necessary information to scale data before running the model
- model_info.txt: File containing some details about the type of the model and its hyperparameters
- prediction.csv: The model's prediction for the input data (or the test section of the input data when training the model)
- confusion_XX.png: Confusion matrix resulting from the above prediction
- Test results.txt: Test metrics resulting from the above prediction
- ROC curve.png: ROC curve resulting from testing the model with multi-match prediction output

As stated in the previous section, only the first three files are required to re-use the model.

# Common operations
This section lists some operations that can be performed with the scripts in this repository, as well as the device they should be performed on. This section assumes that all the repositories from the project are contained in the same folder and that the scripts are being run from the root folder of this repository.

To get more information about the parameters and flags, check the help messages provided by the scripts.

## Training and testing a model with an existing dataset
The following command provides an example of how a regular model can be run:

- Device: PC
- Command: `python IOT/main_train_model.py -t 20 data/6h out/tsf tsf 5 60 multi`

This command will train the TSF model using the 6-hour dataset (which is assumed to be located at _data/6h_), leaving 20% of the data for testing and performing multi-prediction. In order to create the final dataset, it will group data with 5 data points per group and 60 groups per window.

Next, this second command shows how to train a time model:

- Device: PC
- Command: `python IOT/main_train_time_model.py -t 20 data/time-data/6h_balanced.csvh out/tsf tsf multi`

This command works similarly to the first one. It will train the TSF model with the 6-hour time dataset (which is assumed to be located at _data/time-data/6h_balanced.csvh_), leaving 20% of the data for testing and running in multi-prediction mode.

## Running a previously trained model
As an example, this section uses the model trained by the previous section (assumed to be placed in _out/tsf_).

- Device: PC
- Command: `python IOT/main_run_model.py <dataset> out/prediction_multi_tsf results.csv out/tsf`
  - `<dataset>`: Path to the dataset that should be passed to the model

The command shown here uses the regular model, but the time model can be used as well, as long as a time dataset is provided as input.

## Training multiple models at once
In this example, the 6h dataset will be used (assumed to be placed in _data/6h_), and 20% of the data will be used for testing.

- Device: PC
- Command: `python IOT/main_train_multiple_models.py data/6h out/multi 20 multi -mm best`
  - The models will be trained to perform a multi-prediction. To change the prediction type, change the _multi_ parameter to _bool_ or _best_.
  - The `-mm best` flag specifies that models that do not support multi-prediction mode should perform a best match prediction instead.

## Testing multiple previously trained models at once
As an example, this section uses the models trained by the previous section (assumed to be placed in _out/multi_) and the 6h dataset (assumed to be placed on _data/6h_).

- Device: PC
- Command: `python IOT/main_test_multiple_models.py data/6h out/multi out/multi-test`

## Running a model in real time (main device), showing an alert if an attack is detected on any of the end devices
This section assumes there's 3 end devices and that a separate script (usually `IOT_pi/main_loop`) is currently writing their power usage to a separate buffer file for each device.

- Device: Main
- Command: `python IOT/main_run_model_continuous.py -v -i 1 ../IOT_pi/data/data-channel-1/buffer.csv -i 2 ../IOT_pi/data/data-channel-2/buffer.csv -i 3 ../IOT_pi/data/data-channel-3/buffer.csv <model> <delay> none`
  - `<model>`: Path to the folder containing the model and its additional data files
  - `<delay>`: How many seconds to wait between model runs
  - `none` specifies that no special action should be taken (other than printing a message) if an attack is detected. If replaced by `alert`, an alert will be sent to the configured alert server. Check the README file of the _IOT_server_ repository for instructions on how to set up the server receive alerts like these.
  - The buffer data files are assumed to be in _IOT_pi/data_

## Running a model in real time (end device), showing an alert if an attack is detected on the device itself
This section assumes that a separate script (usually `IOT_pi/end_device_loop`) is currently writing the power usage data of the device to a buffer file.

- Device: End
- Command: `python IOT/main_run_model_continuous.py -v -i self ../IOT_pi/data/buffer.csv <model> <delay> none`
  - `<model>`: Path to the folder containing the model and its additional data files
  - `<delay>`: How many seconds to wait between model runs
  - `none` specifies that no special action should be taken (other than printing a message) if an attack is detected. If replaced by `alert`, an alert will be sent to the configured alert server. Check the README file of the _IOT_server_ repository for instructions on how to set up the server receive alerts like these.
  - The buffer data file is assumed to be in _IOT_pi/data/buffer.csv_

## Running the feature selection algorithm
The feature selection script can be started by running `python IOT/main_feature_selection.py <input path> <output path>`.
- `<input path>` should conatin a path to the dataset(s) to use during the process. The dataset should contain all the features that want to be tested. The algorithm will look for the best combination of those features.
- `<output path>` is the path to the folder that will contain the results

Since the process can take a while, the program will create checkpoint folders as it runs, in case the execution is abruptly terminated. In order to resume a prior execution, the `-r` option must be passed to the program. The checkpoint folder are stored under `<output path>/Checkpoints`.

**Important**: The feature selection algorithm is very resource intensive, and should not be run on a regular PC with the default parameters. See section [Known issues and limitations](#known-issues-and-limitations) below for details.

# Known issues and limitations
- Dumped KNN models are architecture-dependant. If the model was trained on a 64-bit machine, it can't run on a 32-bit one.
- Training multiple models in parallel, either by passing the `-np` flag to [main_train_multiple_models.py](IOT/main_train_multiple_models.py) or by running [main_feature_selection.py](IOT/main_feature_selection.py) with the `FeatureSelection > NumProcesses` config option set to anything other than 1, requires a large amount of CPU power and RAM. Lower-end machines might experience significant slowdown or crashes. It is recommended to use single-process training unless you have a high-end computer.
  - The full feature selection process, with unlimited parallel processes and 16 individuals for each iteration of the genetic algorithm, was run on a dedicated machine that was part of the LUSITANIA supercomputer. The script used 32 cores and 32 GB of RAM while running, and therefore should not be launched on a regular PC as it will cause a crash immediately.

# Other questions and answers
Since the repository has a somewhat complex structure, this section lists how to perform some less common operations, as well as how to properly modify some parts of the project.

## How to read the "attacks" value in the data and output files?
The active attacks on a device can be represented in two ways:

### Split representation
In this representation, all the active attacks are listed, each one identified by one or two letters. These are the letters associated to each attack:

- Mining: M
- Login: L
- Encryption: E
- Password: P
- Lite mining: LM
- Flood: F
- Port scan: PS

For example, if the mining and encryption attacks are active, this is represented as "M+E".

This representation is used in the output data produced by the models when they are tested or run.

### Joint representation
In this representation, the set of active attacks is represented with a single integer. Each attack is represented by a single bit, so individual attacks are represented by a power of 2.

For example, if a value is labeled as 5, that implies that attacks #0 (represented as 1) and #2 (represented as 4) are active, since 1 + 4 = 5.

This representation is used on the input files used by the models.

This joint representation of each of the attacks listed above, assuming no other attacks are active, would be the following:

- Mining: 1
- Login: 2
- Encryption: 4
- Password: 8
- Lite mining: 16
- Flood: 32
- Port scan: 64

## How can new classification models be added?
In order to add a new type of model, follow these steps:

1. Create a new value in the `ClassifierType` enum, in [defs/enums.py](IOT/defs/enums.py). The public methods on that enum must also be updated.
   - If you'd like to add a new time classifier, modify the `TimeClassifierType` enum instead.
2. To implement the model, add a new class under the [classifiers](IOT/classifiers) folder that extends `BaseClassifier` and implements the required methods.
   - If you're adding a new time classifier, add the new class under [time_classifiers](IOT/classifiers/time_classifiers) instead, making it inherit from `BaseTimeClassifier`.
3. Modify `ClassifierFactory`, in [classifier_factory.py](IOT/classifiers/classifier_factory.py), to allow instantiating the new classifier class based on the `ClassifierType` values.
   - For time models, modify `TimeClassifierFactory` ([time_classifier_factory.py](IOT/classifiers/time_classifiers/time_classifier_factory.py)) instead.
4. Modify the help text in [main_train_model.py](IOT/main_train_model.py) to list the new model.
   - If you added a time model, modify [main_train_time_model.py](IOT/main_train_time_model.py) instead.

## Is it possible to show the dataset that is passed to a model when training or testing it?
